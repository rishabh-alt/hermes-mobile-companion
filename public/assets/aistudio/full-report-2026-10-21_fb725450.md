# hermes-mobile-companion — full report, 2026-10-21

App build under review: HEAD `3cdd420` ("refactor: improve performance and audio reliability"),
read-only source review in the local QA clone, plus a live connected pass against the Mac
dashboard the same evening. Supersedes nothing — this consolidates the three QA passes in
`qa-report-2026-10-19.md`, the OnDev review mining in
`ondev-review-gap-checklist-2026-10-21.md`, and tonight's connected results.

## 1. Executive summary

The build is healthy: 113/113 tests, ESLint 0 errors, clean UI pass, and all three Oct-19
bugs verified fixed. Tonight the app was exercised against the real dashboard for the first
time: Hermes 0.22.2 answered, and the dashboard is properly fail-closed (everything except
the two public endpoints returns 401 unauthenticated). The remaining work is not stability —
it's reach. The settings UI surfaces 580 of the dashboard schema's 908 config fields (64%);
the other 36% — including all Discord/messaging-platform config and the 94-field display
category — has no app UI at all. Two cheap Oct-19 nits (silent "New session" redirect, stale
Check-host diagnostics) are still present, and the app's biggest structural gaps versus its
own desktop-parity philosophy are: no host file browser, no true push (notifications die
with the app), no LAN↔Tailscale auto-routing, and no gateway-version compatibility warning —
the exact failure that is killing the category-leading competitor.

## 3. Bugs

### Fixed since Oct 19 (verified at `3cdd420`; detail in the QA report's third-pass addendum)
- **Session drawer polling** — now polls every 15 s plus on focus/visibility
  (`session-drawer.tsx:79,93`).
- **Biometric unlock** — now verifies the enrolled credential via `allowCredentials` and an
  assertion-ID check (`app-lock.ts:292–335`, test at `app-lock.test.ts:84`).
- **Backup/restore http inconsistency** — `savedHosts` http entries now throw descriptive
  errors instead of being silently dropped (`config-backup.ts`).
- Also: PIN hash upgraded from FNV-1a to a salted 10,000-round digest with lockout fields;
  chime uses a shared `AudioContext` with `resume()`; lightbox zoom origin fixed.

### Still present (re-checked at `3cdd420`)
1. **"New session" with no host configured still silently redirects to Settings.**
   `session-drawer.tsx:151–155`: `startNew` does a bare `navigate({ to: "/settings" })`
   when unconfigured — no toast, no explanation. The drawer has no toast import at all.
   (Oct-19 addendum item 4.)
2. **Stale "Check host" diagnostics still aren't cleared when the host input changes.**
   Probes are cleared only at the start of a new check (`settings.tsx:137`); the gateway
   URL input's `onChange` (`settings.tsx:700`) only updates config, so old probe rows
   (rendered at `settings.tsx:834–846`) stay on screen after the field is edited or
   cleared, while the Check host button disables again. (Oct-19 addendum item 5.)
3. **Copy nits, all three:** lock screen still says "headless **PC** console"
   (`app-lock-gate.tsx:77`) while the rest of the app says "headless host"
   (`status.tsx:133`, `settings.tsx:1188`); the light theme is still labelled "**daylight**"
   (`settings.tsx:872`); `package.json` name is still the template leftover
   `tanstack_start_ts`. (Oct-19 addendum item 6.)

### New
4. **Configure sections silently truncate at 120 fields.** `readDashboardSection` ends
   with `.slice(0, 120)` (`dashboard.ts:345`). Two sections exceed it against the live
   0.22.2 schema: **Chat** (categories agent+attachments = 132 fields) and **Providers**
   (openrouter+bedrock+auxiliary = 132 fields) — up to a dozen settings per section never
   render, with no indication anything is missing. Which fields drop depends on schema
   order, so the missing set can shift between Hermes releases.
5. **Shiki vendor-syntax chunk is 19.4 MB (3.36 MB gzip)** in the production build
   (third-pass finding, QA report issue #9); `vendor-mermaid` is 3.18 MB (838 KB gzip).
   Chunk organization is better than the old anonymous chunks, but if the syntax chunk
   loads on mobile data it's a heavy first hit. Lazy-load or trim Shiki's language set.

## 4. QoL improvements

- **Auto-scroll during streaming: present** — the OnDev complaint (checklist A5) does not
  apply here. Chat uses a stick-to-bottom conversation component with a scroll-to-bottom
  affordance (`components/ai-elements/conversation.tsx:68–72`).
- **Fix the two stale-feedback items in §3** — both are one-line-class fixes (a toast on
  the unconfigured New-session path; clearing probes on URL change) and both are the kind
  of "why did nothing happen?" friction that reads as broken to a new user.
- **Copy pass** — the §3.3 nits, plus one more found in this pass: the Chat section's
  summary promises "Personality, timezone, reasoning, and attachments"
  (`settings-console.ts:31`), but there is no personality or timezone control anywhere in
  the app (zero grep hits) — both settings live in schema categories the app doesn't map
  (`display.personality`; `timezone` in general). Either surface them or trim the summary.
- **Bundle diet** — lazy-load Shiki/mermaid (§3.5). OnDev's ~1 GB install is the category's
  bloat cautionary tale (checklist A7); this app is lean except for these two chunks.
- **Provider switching** — OnDev users found theirs "rough and confusing" (checklist A6).
  This app's model sheet + per-profile provider/model is comparatively structured
  (inference from the QA passes; not re-tested with a live gateway in this pass) — worth
  one live check once authenticated testing is possible, because it's a named competitor
  pain point.
- **Background survival** — OnDev's most-upvoted complaint (checklist A4) is about the
  app dying when backgrounded. This app persists config/drafts/app-lock state locally
  (verified in earlier passes), so the exposure is mainly the live-notification gap in §5 —
  but an Android soak test (leave a chat streaming, background for 10 min, return) is
  still unrun; see §7.

## 5. Features to add (prioritized)

### P0
1. **Gateway-version compatibility warning on connect.** The app already reads the host
   version — `checkHostUpdate` calls `/api/update/check` with a `/api/status` fallback
   (`dashboard.ts:1000–1013`), shows it in About, and can even apply host updates
   (`dashboard.ts:1015`). What doesn't exist anywhere (grep-verified) is a comparison of
   the gateway version against the range the app build supports, with a "this Hermes is
   newer/older than the app expects" warning. *Why:* version drift is the #1 killer in
   this category — OnDev is stuck on Hermes v17 against v22 gateways and its reviews are
   a wall of connection failures and refund demands (OnDev checklist A1, §E.1). Tonight's
   host is already on 0.22.2; the next Hermes release is exactly when this bites.
2. **True push for approvals (and cron failures).** Today, alerts ride on SSE watch
   streams (`watch.ts` `followHostWatch`) consumed by the Activity and Chat routes,
   surfaced as toasts + the web Notification API (`activity.tsx:68–104`,
   `chat-view.tsx:560–621`). Nothing runs when the app is closed — the app's own
   Notifications section admits it: "A killed app cannot be woken by the host yet"
   (`settings-console.ts`, notifications section). No ntfy/FCM/WebPush/native
   notification bridge exists in the codebase (grep-verified). *Why:* an approval request
   is the one event that blocks the agent; if it only surfaces while the user is already
   looking at the app, the phone-as-primary-client model leaks. The ntfy pattern is the
   proven route in this ecosystem (Herald's herald-push protocol; Rishab's own Oct-18
   IMAP IDLE→ntfy design for email notifications applies the same push-don't-poll logic).

### P1
3. **Timestamps + gap awareness** (Rishab's Oct-18 feature idea #1). Both halves are
   absent today (grep-verified): no date dividers in message rendering
   (`message-list.tsx`, `chat-view.tsx`, `transcript.ts` have no divider/Today/Yesterday
   logic), and no "[time since last message]" context is constructed for the gateway.
   *Why:* his own stated want; also cheap — pure client rendering plus one context line
   on send.
4. **LAN↔Tailscale auto-routing.** A saved host has exactly one `baseUrl` and one
   `dashboardBaseUrl` (`types.ts:63–73`); multiple hosts exist but switching is manual.
   There is no per-host LAN+tailnet pair, no racing, no fallback. *Why:* hermes-relay's
   signature feature (LAN at home, Tailscale away) — chat latency on the home network
   currently pays the tailnet round trip for no reason.
5. **Cross-chat "waiting on you" badge in the drawer.** The Activity screen is already a
   cross-chat inbox — it streams events for all sessions and fetches pending
   approvals/clarifies for the 12 most recent sessions (`activity.tsx:68–120`). But the
   session drawer shows no unread/waiting indicator (rows use `updatedAt` only for
   ordering, `session-drawer.tsx:136`), and nothing surfaces outside the Activity
   screen. *Why:* Herald shipped exactly this in v0.11 ("say when another chat replies
   or waits on you"); the data pipeline here already exists — it's a presentation gap.
6. **Cron-results inbox.** Run history already exists in Jobs (`jobs.tsx:258–346`,
   "Recent runs"), and cron failures toast while the app is open — but there's no
   persistent, push-delivered inbox of job results. *Why:* Herald's v0.10 Inbox (via
   herald-push) is the reference; pairs with P0.2.

### P2
7. **Tablet/large-screen layout pass.** Asked for by name in OnDev's reviews (checklist
   B3); this app's QA has only ever run at phone viewport (390×844).
8. **Setup/compat documentation.** OnDev users punished the absence of docs and the need
   for version-flag workarounds (checklist A2). A one-page "which Hermes versions, which
   URL goes where, what the probes mean" doc ships with P0.1's version story.
9. **QR pairing is already done — keep it.** Not a to-add: host setup already supports
   camera scan, QR-photo upload, paste, and a one-time pairing-code exchange that
   returns the token + dashboard URL (`settings.tsx` ConnectionFields /
   `applyScannedAddress`; `dashboard.ts` `parsePairingInput`/`exchangePairingCode`),
   plus a token-free address QR for sharing (`settings.tsx:508`, `qr.ts`). Listed here
   because it was on the candidate list — it's a strength, ahead of every peer checked.

## 6. What's missing — desktop-parity gaps

Measured against the live Hermes 0.22.2 config schema (908 fields) — the app's stated
philosophy is full desktop parity, so schema areas with no app UI are genuine gaps:

- **Settings coverage: 580/908 fields (64%) are wired to a Configure section; 328 fields
  (36%) in 26 categories have no section at all.** The app maps schema categories to its
  11 host sections in `SECTION_CATEGORIES` (`dashboard.ts`) and renders them generically
  (`dashboard-fields.tsx`). Unmapped, by size: **display 94, discord 42, general 27,
  kanban 18, desktop 16, secrets 15, wake_word 13, monitoring 11, curator 10, lsp 10,
  web 9, moa 9, slack 6, vault 6, bot_desktop 5, proxy 5, worktrees 4, loops 4, x_search 4,
  database 3, vision 3, mattermost 3, matrix 3, logging 3, model_catalog 3, vertex 2.**
- Notable within that list:
  - **Messaging-platform config (discord 42, slack 6, matrix 3, mattermost 3 = 54
    fields).** The Messaging route shows platform state, but no platform *configuration*
    is editable from the phone. Discord alone is the second-largest unmapped category.
  - **display (94)** — the largest unmapped block. Much of it is host TUI/CLI preference
    (inference: `display.tui_*`, `cli_layout` etc. are desktop-terminal concerns), but
    under a strict parity reading it's unsurfaced, and it contains user-facing items
    like `display.personality` (see §4).
  - **secrets + vault provider config (21 fields)** — Bitwarden/1Password integration
    settings. The app has a credential-vault panel for stored credentials (Browser
    section) and write-only env-key panels, but the vault *provider* configuration
    itself isn't editable.
  - **web (9)** — web search/extract backend selection isn't editable from the phone.
  - **kanban config (18)** — the Kanban board route exists; its configuration doesn't.
  - **general (27)** is *partially* covered outside the field renderer: `model` and
    fallbacks are handled by the dedicated Model section (`dashboard-panel.tsx` /
    ModelAdminPanel). The rest (session limits, context-file limits, `timezone`, MCP
    timeouts) is not surfaced.
  - Separately, 53 schema fields are deliberately never rendered by the field renderer
    because their keys match `api_key|token|secret|password` (`dashboard.ts`,
    `readDashboardSection`) — by design; keys go through the write-only env panels.
- **No host file browser.** The route table (13 routes) has no files/workspace route;
  `/artifacts` is agent-produced outputs only — "Images, files and links your Hermes
  agent has produced" (`artifacts.tsx`) — and the Workspace settings section is config
  (terminal category), not browsing. Under the parity philosophy this is the largest
  single missing surface: you cannot browse, view, or download files from the host.
- **No background/push channel** — see §5 P0.2; architecturally this is also a parity
  gap (desktop Hermes surfaces approvals immediately; the phone only does while open).
